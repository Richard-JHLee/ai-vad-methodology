# VAD — 검증 가능한 AI 개발 방법론

> AI를 활용해 개발하더라도 소프트웨어가 사람에게 이해 가능하고, 추적 가능하며, 검증 가능하고, 복구 가능한 상태를 유지하도록 제안하는 공개 개발 방법론입니다.

[English](./README.md) · [핵심 RFC](./rfcs/0001-vad-core.md) · [RFC 0002 증거 모델](./rfcs/0002-vad-v0.2-evidence-model.md) · [기여 안내](./CONTRIBUTING.md)

---

## 왜 VAD가 필요한가?

AI는 개발자가 코드를 분석하는 속도보다 더 빠르게 코드를 생성할 수 있습니다.

이로 인해 소프트웨어 개발에는 새로운 문제가 발생하고 있습니다.

이제 가장 큰 위험은 AI가 정상적으로 작동하는 코드를 만들지 못하는 것이 아닙니다.

오히려 AI가 겉으로는 잘 작동하는 코드를 빠르게 만들어내는 동안, 개발자가 다음 질문에 답하기 어려워지는 것이 더 큰 문제입니다.

* 이 코드는 왜 변경되었는가?
* 시스템의 어느 부분에 영향을 주는가?
* 어디에서 문제가 발생할 수 있는가?
* 장애가 발생하면 어떻게 복구할 것인가?
* 누가 이 변경을 검토하고 승인했는가?

기존의 소프트웨어 개발 원칙은 여전히 중요합니다.

그러나 AI 보조 개발은 코드가 만들어지는 속도와 변경 규모를 크게 증가시킵니다. 기존 방식만으로는 인간의 이해와 검토가 AI의 생성 속도를 따라가기 어려울 수 있습니다.

VAD는 다음 기준을 중심으로 개발 절차를 제안합니다.

> 개발자가 변경 목적, 영향 범위, 실패 지점, 검증 근거와 복구 방법을 설명할 수 있을 때 비로소 소프트웨어 변경이 완료된 것으로 본다.

## VAD란 무엇인가?

**VAD**는 **Verifiable AI Development**의 약자입니다.

한국어로는 **검증 가능한 AI 개발**을 의미합니다.

VAD는 AI 코딩 도구나 자율형 AI 에이전트가 생성한 소프트웨어 변경을 사람이 통제하고 검토하며 안전하게 운영하기 위해 제안하는 개발 방법론입니다.

VAD는 AI 사용을 제한하거나 금지하기 위한 방법론이 아닙니다.

AI가 만든 결과물이 다음 조건을 유지하도록 만드는 것이 목적입니다.

* **이해 가능성**: 사람이 시스템의 동작과 변경 이유를 설명할 수 있어야 합니다.
* **추적 가능성**: 요구사항, 설계 결정, 코드 변경을 서로 연결할 수 있어야 합니다.
* **검증 가능성**: 테스트와 분석 결과를 통해 변경의 적합성을 확인할 수 있어야 합니다.
* **범위 제한성**: 사람이 검토할 수 있는 수준으로 변경 범위가 관리되어야 합니다.
* **복구 가능성**: 문제가 발생하면 변경을 중단하거나 이전 상태로 되돌릴 수 있어야 합니다.
* **책임 명확성**: 최종 승인과 운영 책임은 명확한 사람에게 있어야 합니다.

v0.2는 속성을 추가하지 않습니다. 기존 세 속성을 두껍게 읽습니다. [RFC 0002](./rfcs/0002-vad-v0.2-evidence-model.md)를 참고하십시오.

* **추적 가능성** — 변경 출처, 지시 출처, 에이전트 실행 증거.
* **검증 가능성** — 정확성, 보안, 회귀, 운영 근거(성능 및 운영 비용 포함), 검증 비용(과정 지표).
* **책임 명확성** — 사람 승인, 실행 소유, 롤백 소유.

## 현재 상태

VAD는 현재 초기 제안 단계에 있습니다.

```text
현재 상태: 초안
버전: 0.1
```

VAD는 국제적으로 공인된 표준이나 학술적으로 검증된 공식 개발 프레임워크가 아닙니다.

다음 과정을 통해 공개적으로 발전시키는 방법론입니다.

* 개발자 커뮤니티 토론
* 실제 프로젝트 적용
* 비판과 반례 수집
* 장애 및 실패 사례 분석
* 소프트웨어 실무자의 기여

VAD에 대한 반대 의견과 비판도 환영합니다.

VAD가 이미 완성된 정답임을 주장하는 것이 목적이 아닙니다.

AI 보조 개발 환경에서 어떤 절차가 실제로 도움이 되고, 어떤 절차가 불필요한지 함께 검증하는 것이 목적입니다.

# VAD 7단계 개발 절차

VAD는 다음 일곱 단계를 기본 개발 절차로 제안합니다.

```text
1. 요구사항 정의
2. 시스템 구조 분석
3. 변경 범위 제한
4. 통제된 코드 생성
5. 변경 지도 작성
6. 자동 및 수동 검증
7. 단계적 배포
```

---

## 1. 요구사항 정의

AI에게 코드를 작성하도록 요청하기 전에 기대하는 동작을 명확히 정의합니다.

요구사항에는 다음 내용이 포함되어야 합니다.

* 기능을 만드는 목적
* 입력값과 출력값
* 사용자 역할과 권한
* 정상 처리 조건
* 실패 처리 조건
* 데이터 변경 규칙
* 보안 요구사항
* 성능 기준
* 복구 요구사항
* 완료 조건

### 핵심 질문

> 이 기능은 정확히 무엇을 해야 하며, 어떤 조건에서는 실패하거나 처리를 거부해야 하는가?

AI는 잘못된 요구사항도 매우 빠르고 정교하게 구현할 수 있습니다.

따라서 AI 보조 개발에서는 코드 생성 능력보다 요구사항의 품질이 더 중요할 수 있습니다.

이 단계 안에서의 흐름입니다. 새로운 최상위 단계가 아닙니다.

```text
요구사항 정의
  → 모호함 탐지
  → 요구사항 명확화
  → 수락 기준
```

구현은 이 단계가 아니라 4단계(통제된 코드 생성)에 속합니다.

**차단 모호함(blocking ambiguity)**은 해소되지 않은 요구사항 불확실성으로서, 다음 중 하나 이상을 실질적으로 바꿀 수 있는 경우입니다: 구현 범위, 수락 기준, 보안 또는 개인정보 동작, 데이터 처리, 권한 또는 인가, 외부에서 관찰 가능한 동작, 롤백 또는 운영 위험. 차단이 아닌 모호함은 수용된 가정으로 기록할 수 있습니다.

해소되지 않은 차단 모호함은 중단 조건입니다. 코드 생성은 모호함이 (1) 명확화되거나 (2) 책임 있는 사람이 잔여 위험으로 명시적으로 수용하기 전까지 진행하지 않습니다. 알려진 모호함, 빠진 정보, 가정, 사람 확인이 필요한 질문, 발견된 암묵적 요구사항은 위험 수준에 맞게 기록합니다. [RFC 0002](./rfcs/0002-vad-v0.2-evidence-model.md)를 참고하십시오.

## 2. 시스템 구조 분석

코드 생성을 시작하기 전에 기존 시스템을 분석합니다.

다음 항목을 파악해야 합니다.

* 관련 파일
* 기능 진입 지점
* API 경로
* 함수 및 서비스 호출 관계
* 데이터 흐름
* 데이터베이스 변경 범위
* 외부 시스템 의존성
* 인증 및 권한 경계
* 백그라운드 작업
* 영향을 받는 앱과 클라이언트
* 기존 테스트

### 필수 결과물

구현 전에 AI 또는 개발자가 간단한 시스템 지도를 작성해야 합니다.

```text
사용자 요청
    ↓
라우트
    ↓
컨트롤러
    ↓
애플리케이션 서비스
    ↓
도메인 로직
    ↓
저장소
    ↓
데이터베이스
    ↓
응답
```

### 핵심 질문

> 이번 변경으로 영향을 받을 수 있는 시스템 영역은 어디인가?

## 3. 변경 범위 제한

AI가 생성하는 변경은 사람이 검토하고 이해할 수 있는 크기로 제한해야 합니다.

기본적으로 다음 원칙을 권장합니다.

* 한 번에 하나의 기능이나 문제만 처리합니다.
* 가능하면 주요 변경 파일을 3~5개 수준으로 제한합니다.
* 기능 개발과 관련 없는 리팩터링을 함께 수행하지 않습니다.
* 승인하지 않은 라이브러리와 의존성을 추가하지 않습니다.
* 관련 없는 파일의 포맷을 변경하지 않습니다.
* 명시적인 승인 없이 전체 아키텍처를 다시 설계하지 않습니다.

파일 수 제한은 절대적인 규칙이 아닙니다.

변경 규모가 커질수록 더 명확한 분리, 검토 자료와 검증 근거가 필요하다는 의미입니다.

### 핵심 원칙

> 명확하게 설명하기 어려울 정도로 큰 변경이라면 안전하게 승인하기에도 너무 큰 변경일 가능성이 높다.

---

## 4. 통제된 코드 생성

AI는 승인된 요구사항과 변경 범위 안에서만 코드를 생성해야 합니다.

구현을 시작하기 전에 AI는 다음 내용을 먼저 제시해야 합니다.

1. 수정할 파일 목록
2. 각 파일을 수정해야 하는 이유
3. 수정하지 않을 파일과 영역
4. 구현 과정에서 사용하는 가정
5. 예상되는 위험
6. 추가하거나 실행할 테스트
7. 복구 또는 롤백 방법

개발자는 이 계획을 검토한 후 코드 생성을 승인합니다.

### AI 요청 예시

```text
코드를 작성하기 전에 기존 구현을 먼저 분석하라.

변경을 시작하기 전에 다음 내용을 작성하라.

1. 현재 기능의 실행 흐름
2. 변경이 필요한 파일
3. 각 파일의 변경 이유
4. 보안 및 데이터 위험
5. 추가할 테스트
6. 장애 발생 시 복구 방법

관련 없는 파일은 수정하지 않는다.
기능 개발과 리팩터링을 동시에 수행하지 않는다.
변경 범위를 확대해야 한다면 코드를 작성하기 전에 이유를 설명하고 중단한다.
```

`AGENTS.md`, `CLAUDE.md`, 저장소 지시, 지속적 시스템 프롬프트, 지속적 에이전트 규칙과 같은 **지속적** AI 지시에는, 이 변경이 그 지시에 **의존하거나 수정한** 경우에만 **지시 출처(instruction provenance)**를 기록합니다: 규칙, 존재하는 이유, 막는 실패나 위험, 도입 시점, 범위, 제거 조건. 의미 있는 모든 **지속적** 지시의 이유를 기록합니다. 임시 대화 프롬프트는 범위 밖입니다. 파일이 존재한다는 이유만으로 모든 지시 파일을 복사하거나 문서화하지 않습니다. 영구 축적 기억이 아니라 유지보수 대상 소프트웨어 산출물로 취급합니다. [RFC 0002](./rfcs/0002-vad-v0.2-evidence-model.md)를 참고하십시오.

에이전트가 실행했다면 실행 중에 **에이전트 실행 증거**를 남깁니다. 깊이는 [위험 수준](./docs/risk-levels.md)을 따릅니다. 이 기록은 단계를 가로지릅니다(변경 지도의 포인터 + 검증 보고서의 상세). 검증 결과가 아니며 여덟 번째 워크플로 단계도 아닙니다. 비밀값, 토큰, 자격 증명, 개인 키, 민감 페이로드 내용은 기록하지 않습니다.

## 5. 변경 지도 작성

모든 AI 보조 개발 변경에는 변경 지도를 작성하는 것을 권장합니다.

변경 지도는 무엇이 어떻게 변경되었으며, 각 변경이 어떤 요구사항과 연결되는지 설명하는 문서입니다.

### 변경 지도 예시

| 파일                           | 변경 내용          | 변경 이유      | 주요 위험      |
| ---------------------------- | -------------- | ---------- | ---------- |
| `routes/api.php`             | 구독 상태 조회 경로 추가 | 신규 API 제공  | 인증되지 않은 접근 |
| `SubscriptionController.php` | 요청 처리 메서드 추가   | API 요청 처리  | 입력값 검증 실패  |
| `SubscriptionService.php`    | 구독 상태 처리 로직 추가 | 비즈니스 규칙 적용 | 잘못된 상태 전환  |
| `SubscriptionTest.php`       | 테스트 추가         | 기능 및 권한 검증 | 예외 조건 누락   |

변경 지도는 다음 질문에 답할 수 있어야 합니다.

* 무엇이 변경되었는가?
* 왜 변경되었는가?
* 어떤 요구사항을 충족하는가?
* 어떤 문제가 발생할 수 있는가?
* 어떻게 검증했는가?
* 문제가 생기면 어떻게 되돌릴 수 있는가?

5단계는 **변경 출처**, **지시 출처**, 에이전트가 실행한 경우 **에이전트 실행 증거 포인터**를 함께 기록합니다. 에이전트 실행 증거 자체는 단계를 가로지르며, 검증 결과가 아닙니다.

---

## 6. 자동 및 수동 검증

AI가 테스트를 생성하고 모든 테스트가 통과했다고 보고하더라도, 그 자체만으로 검증이 완료된 것은 아닙니다.

VAD는 검증을 여러 단계로 분리합니다.

### 6.1 정적 검증

다음 항목을 확인합니다.

* 컴파일 성공 여부
* 타입 안정성
* 린트 및 코드 규칙
* 의존성 변경
* 위험한 API 사용
* 비밀키 및 민감정보 노출
* 일반적인 보안 취약점
* 사용하지 않는 코드

### 6.2 기능 검증

다음 내용을 확인합니다.

* 정상 입력 처리
* 잘못된 입력 처리
* 사용자 권한
* 경계값
* 중복 요청
* 실패 처리
* 오류 메시지
* 부분 성공 및 부분 실패 상황

### 6.3 회귀 검증

기존 기능이 정상적으로 유지되는지 확인합니다.

다음 영역을 검토합니다.

* 관련 API
* 기존 사용자 흐름
* 데이터베이스 호환성
* 이전 앱 버전
* 백그라운드 작업
* 외부 서비스 연동
* 캐시
* 기존 테스트

### 6.4 운영 검증

실제 운영 환경에서 안전하게 관리할 수 있는지 확인합니다.

다음 항목을 검토합니다.

* 로그
* 모니터링
* 알림
* 성능
* 외부 API 사용량
* 서버 및 AI 비용
* 데이터베이스 마이그레이션 안전성
* 롤백 준비
* 장애 대응 절차
* 담당자 지정

6단계는 검증 **근거**와 **지표**를 사용합니다. 다음이 모두 검증 *결과*는 아닙니다.

* 정확성 근거
* 보안 근거
* 회귀 근거
* 운영 근거(상위 제목; 성능 근거와 운영 비용 — 머지 이후 런타임·인프라 비용 — 포함)
* 검증 비용(생애주기 과정 지표이며, 변경이 올바르다는 증거가 아님)

### 운영 근거 (Operational Evidence)

**운영 근거**가 상위 제목입니다. **성능 근거**는 측정 가능한 런타임 영향을 포함할 수 있습니다. 변경과 관련된 지표만 기록합니다. 성능·비용·용량이 범위에 없으면 N/A로 충분합니다.

예:

* CPU 사용량
* 메모리 사용량
* 데이터베이스 쿼리
* 할당
* 지연 시간
* 외부 API 호출
* 인프라 비용

기능 테스트를 통과했다고 해서 생성된 코드가 운영상 효율적이라는 뜻은 아닙니다.

### 검증 비용 (Verification Cost)

**검증 비용**은 변경에 충분한 확신을 갖기 위한 **머지 이전** 노력과 자원 비용입니다. 생애주기 **과정 지표**이며, 변경이 올바르다는 증거가 아닙니다.

**운영 비용**은 **머지 이후** 런타임·인프라 비용이며 운영 근거에 기록합니다.

AI 보조 생산성은 코드 생성 시점이 아니라 변경 생애주기 전체에서 평가해야 합니다.

생성이 빨라져도 검토·검증·운영 비용이 비례 이상으로 늘면 그 변경이 더 생산적이라고 단정할 수 없습니다.

선택적 대리 지표로 검토 반복, 리뷰 댓글, 머지까지 걸린 시간(대기 시간 포함 가능), 테스트 실행 비용, 정적 분석 소견 *건수* 또는 해소 노력(소견 자체는 검증 결과), 사람 검토 노력, 해소되지 않은 검증 불확실성을 기록할 수 있습니다. **낮은 위험 변경마다 모든 항목을 측정할 필요는 없습니다.** 깊이는 [위험 수준](./docs/risk-levels.md)을 따릅니다.

에이전트 실행 증거는 6단계 검증 층이 아닙니다. 단계를 가로지르는 실행 증거이며, 검증과 책임의 입력입니다. 변경 지도에서 가리키고 검증 보고서에서 상세를 적습니다. 깊이는 위험 수준을 따르며, 에이전트가 도운 모든 변경에 전체 항목을 요구하지 않습니다.

### 핵심 원칙

> AI가 작성한 설명과 테스트는 검증에 사용할 자료이지, 검증이 완료되었다는 결과가 아니다.

## 7. 단계적 배포

테스트를 통과했다고 해서 운영 환경에서 반드시 안전한 것은 아닙니다.

영향이 큰 변경은 일부 환경과 사용자부터 단계적으로 배포해야 합니다.

일반적인 배포 순서는 다음과 같습니다.

```text
로컬 개발 환경
    ↓
개발 서버
    ↓
내부 사용자
    ↓
일부 사용자
    ↓
확대 배포
    ↓
전체 운영 환경
```

다음 방법을 활용할 수 있습니다.

* 기능 플래그
* 카나리 배포
* 점진적 사용자 확대
* 데이터베이스 백업
* 주요 상태 지표 확인
* 오류율 기준 설정
* 자동 롤백 조건
* 담당자와 대응 절차 지정

### 핵심 질문

> 이 변경이 모든 사용자에게 영향을 주기 전에 중단하거나 되돌릴 수 있는가?

# VAD 개발 완료 기준

다음 조건만 충족했다고 해서 개발이 완료된 것은 아닙니다.

* 코드가 컴파일됩니다.
* 자동 테스트가 통과합니다.
* AI가 성공했다고 보고합니다.
* 기능이 한 번 정상 동작합니다.
* 화면이 예상대로 표시됩니다.

VAD에서 개발 완료를 승인하는 담당자는 다음 항목을 설명할 수 있어야 합니다.

1. **목적**: 왜 이 변경이 필요한가?
2. **범위**: 무엇이 변경되었는가?
3. **영향**: 어떤 시스템과 사용자에게 영향을 주는가?
4. **실패**: 어디에서 어떻게 실패할 수 있는가?
5. **근거**: 어떤 방식으로 검증했는가?
6. **복구**: 어떻게 기능을 중단하거나 이전 상태로 되돌릴 수 있는가?
7. **책임**: 누가 변경을 승인하고 운영하는가?

# 위험도에 따른 적용

모든 변경에 동일한 수준의 절차를 적용할 필요는 없습니다.

VAD는 변경 위험에 따라 절차 강도를 조절하는 것을 권장합니다.

| 위험 수준 | 예시                          | 권장 절차                        |
| ----- | --------------------------- | ---------------------------- |
| 낮음    | 문구 변경, 독립된 UI 조정            | 변경 지도와 기본 테스트                |
| 보통    | 신규 API, 비즈니스 규칙 변경          | 요구사항 계약서, 테스트, 영향도 분석        |
| 높음    | 인증, 결제, 구독, 데이터 마이그레이션      | 모든 핵심 문서, 보안 검토, 단계적 배포      |
| 매우 높음 | 금융·의료 데이터, 인프라, 되돌릴 수 없는 변경 | 별도 검토자, 복구 훈련, 모니터링 및 명시적 승인 |

VAD의 목적은 불필요한 문서를 만드는 것이 아닙니다.

발생 가능한 피해에 비례하여 개발 통제 수준을 높이는 것이 목적입니다.

# VAD 핵심 원칙

1. 코드를 생성하기 전에 시스템을 분석합니다.
2. 한 번에 하나의 기능이나 문제만 변경합니다.
3. 기능 개발과 관련 없는 리팩터링을 분리합니다.
4. 의미 있는 모든 변경의 이유를 기록합니다.
5. AI 출력은 검증되기 전까지 신뢰하지 않습니다.
6. AI가 작성한 코드를 동일한 AI만 검토하도록 하지 않습니다.
7. 테스트뿐 아니라 운영과 복구 조건도 정의합니다.
8. 위험이 큰 변경은 단계적으로 배포합니다.
9. 최종 승인과 책임은 사람에게 둡니다.
10. 설명할 수 없는 대규모 변경보다 이해할 수 있는 작은 변경을 우선합니다.

---

# VAD가 아닌 것

VAD는 다음을 의미하지 않습니다.

* 애자일 개발을 대체하는 방법론이 아닙니다.
* DevOps를 대체하지 않습니다.
* 테스트 주도 개발을 대체하지 않습니다.
* AI 코드의 안전성을 보장하지 않습니다.
* 모든 코드 한 줄을 사람이 직접 확인하라는 의미가 아닙니다.
* 자율형 AI 에이전트를 금지하지 않습니다.
* 완성된 국제 표준이 아닙니다.
* 모든 프로젝트에 동일한 문서 작업을 강제하지 않습니다.

VAD는 기존 소프트웨어 공학 원칙을 대체하는 것이 아니라, AI가 생성하는 변경에 대한 통제와 검증을 강화하기 위해 보완하는 방법론입니다.

---

# 공개 토론이 필요한 질문

VAD는 완성된 결론이 아니라 공개 토론을 위한 초기 제안입니다.

다음 질문은 실제 사례와 커뮤니티 논의가 필요합니다.

## 이해와 승인

* 개발자가 완전히 이해하지 못한 AI 생성 코드를 배포해도 되는가?
* 개발자는 어느 수준까지 코드를 이해해야 배포를 승인할 수 있는가?
* 전체 코드 경로를 이해해야 하는가?
* 아키텍처, 영향 범위, 실패 지점과 롤백 방법을 이해하면 충분한가?

## 검증

* AI가 생성한 테스트를 독립적인 검증 결과로 인정할 수 있는가?
* 다른 AI 모델의 코드 리뷰는 독립적인 검증으로 볼 수 있는가?
* 사람이 반드시 직접 확인해야 하는 영역은 무엇인가?
* 테스트 통과 외에 어떤 운영 검증이 필요한가?

## 변경 범위

* AI의 코드 변경 파일 수를 제한해야 하는가?
* 파일 수보다 코드 줄 수를 제한하는 것이 더 효과적인가?
* 대규모 아키텍처 변경을 어떻게 작은 단계로 분리할 것인가?
* AI가 변경 범위를 스스로 확대하지 못하도록 어떻게 통제할 것인가?

## 책임

* 자율형 AI 에이전트가 장애를 발생시키면 누가 책임져야 하는가?
* AI가 참여한 모든 Pull Request에 사람 담당자를 지정해야 하는가?
* 조직은 AI가 생성한 코드의 비율과 참여 내역을 기록해야 하는가?
* AI 코드에 대한 승인 책임을 팀과 개인 중 어디에 둘 것인가?

## 개발 절차

* VAD는 소규모 팀에 지나친 부담을 주는가?
* 반드시 필요한 VAD 문서는 무엇인가?
* 어떤 절차를 자동화할 수 있는가?
* 기존 CI/CD와 VAD를 어떻게 연결할 것인가?
* 기존 Agile, TDD, DevOps와 어떤 차이가 있어야 하는가?

# 첫 번째 토론 주제

## 개발자가 완전히 이해하지 못한 AI 생성 코드를 배포해도 되는가?

AI는 개발자가 코드를 분석하는 속도보다 더 빠르게 코드를 생성할 수 있습니다.

AI 보조 개발이 일반적인 방식이 되어갈수록 다음 질문이 중요해집니다.

> 개발자는 AI가 생성한 코드를 어느 수준까지 이해해야 운영 환경 배포를 승인할 수 있을까요?

자동화된 테스트가 모두 통과하면 충분할까요?

개발자는 모든 코드 경로를 직접 이해해야 할까요?

아니면 시스템 구조, 영향 범위, 실패 지점과 롤백 방법을 이해하는 것으로 충분할까요?

신뢰와 검증의 경계를 어디에 두어야 할까요?

다음과 같은 의견을 환영합니다.

* 실제 프로젝트 경험
* VAD에 대한 반론
* AI 코드로 인한 장애 사례
* 효과가 없었던 검증 방식
* 실무적으로 가능한 개선안
* 소규모 팀의 현실적인 적용 방법

# 제안 배경과 저작자 표시

VAD는 AI가 개발자의 분석 속도보다 빠르게 소프트웨어를 변경하면서 인간의 이해와 통제력이 약해질 수 있다는 문제의식에서 시작되었습니다.

초기 제안은 **Richard J. H. Lee**가 ChatGPT와의 논의를 바탕으로 정리했습니다.

VAD는 다음과 같이 소개하는 것을 권장합니다.

> AI 보조 소프트웨어 개발을 검증 가능하고 추적 가능하게 만들기 위해 제안된 공개 개발 방법론

VAD를 국제적으로 승인되거나 학술적으로 인증된 표준으로 표현해서는 안 됩니다.

## 토론에 참여해 주십시오

다음과 같은 의견이 있다면 Discussion 또는 Issue를 열어 주십시오.

* VAD 원칙에 동의하지 않는 경우
* 불필요한 단계가 있다고 판단하는 경우
* AI 생성 코드로 인한 실제 운영 장애를 경험한 경우
* 더 효과적인 검증 방법이 있는 경우
* 적용 사례를 공유하고 싶은 경우
* 새로운 템플릿이나 자동화 도구를 제안하는 경우

VAD는 단순한 동의가 아니라 실제 증거, 비판과 적용 경험을 통해 발전해야 합니다.
