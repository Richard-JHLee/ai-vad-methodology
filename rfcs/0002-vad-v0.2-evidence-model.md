# RFC 0002: VAD v0.2 Evidence Model

- Status: Draft
- Version: 0.2 (proposal; core remains Draft 0.1 until this RFC is accepted)
- Author: Richard J. H. Lee
- Created: 2026-08-15
- Relates to: [RFC 0001](./0001-vad-core.md)

## Summary

This RFC extends VAD’s evidence and verification model without changing the six
core properties, the seven workflow stages, or the five required artifacts.

It incorporates:

1. Requirement Ambiguity / Clarification
2. Verification Cost
3. Performance Evidence
4. Instruction Provenance
5. Agent Execution Evidence

These are fields attached to existing stages and templates, scaled by risk.

## Motivation

RFC 0001 already requires that a change can be explained, verified, and recovered.
In AI-assisted work, gaps still appear:

- Ambiguous requirements are implemented at high speed.
- Persistent AI instructions (`AGENTS.md`, `CLAUDE.md`, system prompts) accumulate
  without recorded purpose or removal criteria.
- Agent tool use, MCP access, and permissions are invisible after the fact.
- Faster generation is treated as productivity even when verification cost rises.
- Performance is ticked as done without measurable operational evidence.

## Non-goals

- Do not add a seventh core property alongside Understandable, Traceable,
  Verifiable, Limited, Recoverable, and Accountable.
- Do not add an eighth workflow stage.
- Do not add a sixth *required* artifact.
- Do not treat agent execution evidence as a verification *result*.
- Do not rewrite RFC 0001.
- Do not bump documented Version from Draft 0.1 until this RFC is accepted.

## Proposal

V0.2 thickens three existing properties; it does not rename or add them:

| Property | v0.2 reading |
| -------- | ------------ |
| Traceable | Change provenance, instruction provenance, agent execution evidence |
| Verifiable | Correctness, security, regression, performance evidence, operational cost, verification cost |
| Accountable | Human approval, execution ownership, rollback ownership |

### Mapping (no eighth stage)

| Concept | Where it lives | Artifact |
| ------- | -------------- | -------- |
| Requirement Ambiguity / Clarification | Inside Stage 1 | Requirement Contract |
| Instruction Provenance | Stages 4–5 | Change Map |
| Change provenance + pointer to agent execution | Stage 5 | Change Map |
| Correctness, security, regression, performance evidence, operational cost, verification cost | Stage 6 | Verification Report |
| Agent Execution Evidence | Cross-stage (not a stage) | Change Map pointer + Verification Report detail |

Nested view of the **existing** seven stages:

```text
1. Requirement Definition
      → Ambiguity Detection
      → Requirement Clarification
      → Acceptance Criteria
2. System Analysis
3. Change Scope Limitation
4. Controlled Code Generation
5. Change Mapping
      - change provenance
      - instruction provenance
      - pointer to agent execution evidence
6. Automated and Human Verification
      - correctness
      - security
      - regression
      - performance evidence
      - operational cost
      - verification cost
7. Progressive Deployment
      - observe / recover
```

Agent Execution Evidence sits beside stages 4–6. It is produced during agent
execution. It is referenced by the Change Map and the Verification Report. It
is not an eighth box in the numbered workflow.

### Requirement Ambiguity / Clarification

Strengthen Stage 1. The Requirement Contract captures:

- Known ambiguities
- Missing information
- Assumptions made
- Questions requiring human clarification
- Implicit requirements discovered

Flow (still Stage 1):

Requirement Definition → Ambiguity Detection → Requirement Clarification
→ Acceptance Criteria → Implementation

Unresolved blocking ambiguity is a stop condition.

### Instruction Provenance

Extend Traceable. Persistent AI instructions (`AGENTS.md`, `CLAUDE.md`,
repository instructions, system prompts, persistent agent rules) record:

- the rule
- why the rule exists
- the failure or risk it prevents
- when it was introduced
- its scope
- when it may be removed

Core idea: record the reason for every meaningful instruction. Treat AI
instructions as maintainable software artifacts rather than permanent
accumulated memory.

### Agent Execution Evidence

Cross-stage execution evidence. **Not** a verification result. **Not** a
workflow stage.

It records what executed the change and serves as input to verification and
accountability. Record when applicable:

- initiating human
- agent/model used
- delegated agents
- tools invoked
- MCP servers accessed
- permissions granted
- external systems accessed
- generated artifacts
- verification results (as inputs, not conclusions)
- human approvals
- execution cost
- rollback owner

Preferred placement:

- Stage 5 Change Map — change provenance, instruction provenance, **pointer**
  to agent execution evidence
- Stage 6 Verification — correctness, security, regression, performance
  evidence, operational cost, verification cost (**not** agent execution as a
  verification layer)
- Agent Execution Evidence — detail in the Verification Report; pointer in the
  Change Map

### Verification Cost

Strengthen Verifiable. AI-assisted development should evaluate not only whether
a change is correct, but also how expensive it is to verify.

AI-assisted productivity must be evaluated across the full change lifecycle,
not only at the point of code generation.

A change is not necessarily more productive if faster generation creates
disproportionate review, verification, or operational cost.

Faster generation is not an improvement if the saved generation cost is
transferred into disproportionate verification cost.

Measurable fields (risk-gated; **not** mandatory for every Low-risk change):

- reviewer iterations
- review comments
- time to merge
- test execution cost
- static-analysis findings
- human review effort
- unresolved verification uncertainty

### Performance Evidence

Expand operational verification so performance and operational cost are explicit
evidence. For performance-sensitive changes, consider:

- CPU usage
- memory usage
- database queries
- allocations
- latency
- external API calls
- infrastructure cost

Passing functional tests does not prove that generated code is operationally
efficient.

### Risk gating

| Evidence | Low | Medium | High / Critical |
| -------- | --- | ------ | --------------- |
| Ambiguity / clarification | Optional one-liner | If AI-assisted | Required; blocking questions resolved |
| Instruction provenance | If instruction files change | If AI-assisted | Required if instruction files exist or change |
| Agent execution evidence | If an agent ran | If an agent ran | Required if an agent ran |
| Verification cost | Skip or one line; not every field | Brief | Required |
| Performance / operational evidence | Only if in scope | If in scope | Required when performance/cost/capacity is in scope |

## Alternatives

- New workflow stage 8 (Evidence Pack or Agent Execution): rejected; dilutes
  the seven-stage model. Agent execution evidence is cross-stage, not a stage.
- Sixth required artifact: rejected; duplicates Change Map and Verification Report.
- Seventh core property (for example “Economical”): rejected; verification cost
  strengthens Verifiable rather than adding a property.
- Treating agent logs as a verification result: rejected; they are inputs.

## Risks

- Template bloat and checklist theater (especially mandatory Low-risk metrics).
- Recording prompts, MCP payloads, or logs that contain secrets.
- Treating agent execution records as proof of correctness.

Mitigations: risk gating, no-secrets rule, explicit “cross-stage input, not
result” language.

## Migration Impact

Additive. Existing 0.1 artifacts remain valid. Teams may ignore new rows on
historical changes. Documented version stays Draft 0.1 until this RFC is
accepted.

## Open Questions

- How much of an agent execution record must be retained, and for how long?
- Should verification cost use hours, story points, or mixed qualitative fields?
- Which operational metrics are minimum for API vs batch vs mobile clients?
- Can CI attach verification-cost and performance blocks automatically?
- Should instruction provenance eventually use the ADR template for large rule
  changes?
