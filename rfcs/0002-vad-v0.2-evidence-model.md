# RFC 0002: VAD v0.2 Evidence Model

- Status: Draft
- Version: 0.2 (proposal; core remains Draft 0.1 until this RFC is accepted)
- Author: Richard J. H. Lee
- Created: 2026-08-15
- Relates to: [RFC 0001](./0001-vad-core.md)

## Summary

This RFC extends VAD’s evidence and verification model without changing the six
core properties, the seven workflow stages, or the five required artifacts.

It incorporates:

1. Requirement Ambiguity / Clarification
2. Verification Cost
3. Operational Evidence (parent; includes Performance Evidence and operational cost)
4. Instruction Provenance
5. Agent Execution Evidence

These are fields attached to existing stages and templates, scaled by risk.

## Motivation

RFC 0001 already requires that a change can be explained, verified, and recovered.
This RFC is motivated by the following **hypotheses and observations** (see
Empirical status). They are not cited empirical results:

- Ambiguous requirements can be implemented at high speed.
- Persistent AI instructions (`AGENTS.md`, `CLAUDE.md`, persistent system
  prompts) may accumulate without recorded purpose or removal criteria.
- Agent tool use, MCP access, and permissions may be invisible after the fact.
- Faster generation may be treated as productivity even when verification
  cost rises.
- Performance may be ticked as done without measurable operational evidence.

## Non-goals

- Do not add a seventh core property alongside Understandable, Traceable,
  Verifiable, Limited, Recoverable, and Accountable.
- Do not add an eighth workflow stage.
- Do not add a sixth *required* artifact.
- Do not treat agent execution evidence as a verification *result*.
- Do not treat verification cost as evidence that the change is correct.
- Do not present operational cost as a sibling verification result; it lives
  under Operational Evidence.
- Do not rewrite RFC 0001.
- Do not bump documented Version from Draft 0.1 until this RFC is accepted.

## Proposal

v0.2 thickens three existing properties; it does not rename or add them:

| Property | v0.2 reading |
| -------- | ------------ |
| Traceable | Change provenance, instruction provenance, agent execution evidence |
| Verifiable | Correctness, security, regression, operational evidence (including performance and operational cost), verification cost as a process measure |
| Accountable | Human approval, execution ownership, rollback ownership |

### Mapping (no eighth stage)

| Concept | Where it lives | Artifact |
| ------- | -------------- | -------- |
| Requirement Ambiguity / Clarification | Inside Stage 1 | Requirement Contract |
| Instruction Provenance | Stages 4–5 | Change Map |
| Change provenance + pointer to agent execution | Stage 5 | Change Map (file map is the provenance record) |
| Correctness, security, regression evidence | Stage 6 | Verification Report |
| Operational Evidence (performance + operational cost) | Stage 6 | Verification Report |
| Verification Cost (process measure) | Stage 6 | Verification Report |
| Agent Execution Evidence | Cross-stage (not a stage) | Change Map pointer + Verification Report detail |

Nested view of the **existing** seven stages:

```text
1. Requirement Definition
      → Ambiguity Detection
      → Requirement Clarification
      → Acceptance Criteria
2. System Analysis
3. Change Scope Limitation
4. Controlled Code Generation
5. Change Mapping
      - change provenance (file map)
      - instruction provenance
      - pointer to agent execution evidence
6. Automated and Human Verification
      - correctness evidence
      - security evidence
      - regression evidence
      - operational evidence (performance + operational cost)
      - verification cost (process measure)
7. Progressive Deployment
      - observe / recover
```

Agent Execution Evidence sits beside stages 4–6. It is produced during agent
execution. It is referenced by the Change Map and the Verification Report. It
is not an eighth box in the numbered workflow.

### Requirement Ambiguity / Clarification

Strengthen Stage 1. The Requirement Contract may capture:

- Known ambiguities
- Missing information
- Assumptions made
- Questions requiring human clarification
- Implicit requirements discovered

These fields are **not** mandatory for every change. Depth follows risk.

Flow (still Stage 1; **does not include Implementation**):

```text
Requirement Definition
  → Ambiguity Detection
  → Requirement Clarification
  → Acceptance Criteria
```

Implementation belongs to Stage 4 (Controlled Code Generation).

A **blocking ambiguity** is an unresolved requirement uncertainty that could
materially change one or more of:

- implementation scope,
- acceptance criteria,
- security or privacy behavior,
- data handling,
- permissions or authorization,
- externally observable behavior,
- rollback or operational risk.

Non-blocking ambiguity may be recorded as an accepted assumption.

Unresolved blocking ambiguity is a stop condition. Code generation must not
proceed until the ambiguity is either:

1. clarified, or
2. explicitly accepted by the responsible human as residual risk.

### Instruction Provenance

Extend Traceable. Instruction Provenance applies **only** to persistent AI
instructions:

- `AGENTS.md`
- `CLAUDE.md`
- repository instructions
- persistent system prompts
- persistent agent rules

Temporary conversational prompts are out of scope.

Record, for each such instruction this change **relied on or modified**:

- the rule
- why the rule exists
- the failure or risk it prevents
- when it was introduced
- its scope
- when it may be removed

Core idea: record the reason for every meaningful **persistent** instruction
that this change relied on or modified. Do not copy or document every existing
instruction file simply because it exists. Treat persistent AI instructions as
maintainable software artifacts rather than permanent accumulated memory.

### Agent Execution Evidence

Cross-stage execution context. **Not** a verification result. **Not** a
workflow stage. **Not** a sixth required artifact.

It records what executed the change and serves as input to verification and
accountability. Canonical rollback owner lives in Verification Report →
Approval. This record uses **accountable owner**.

Do not record secrets, tokens, credentials, private keys, or sensitive payload
contents. Record identifiers or references instead.

Depth scales by risk. Do not require the full field list for every
agent-assisted change:

- **Low** (if an agent executed the change): initiating human; agent/model;
  accountable owner
- **Medium:** add tools or persistent instructions when relevant
- **High / Critical:** full set when the agent accessed elevated permissions,
  MCP servers, external systems, production systems, or sensitive credentials
  or data

Full fields, when applicable:

- initiating human
- agent/model used
- delegated agents
- tools invoked
- MCP servers accessed
- permissions granted
- external systems accessed
- generated artifacts
- verification results (as inputs, not conclusions)
- human approvals
- execution cost
- accountable owner

Preferred placement:

- Stage 5 Change Map — change provenance (file map), instruction provenance,
  **pointer** to agent execution evidence
- Stage 6 Verification — correctness, security, regression, operational
  evidence, verification cost (**not** agent execution as a verification layer)
- Agent Execution Evidence — detail in the Verification Report; pointer in the
  Change Map

### Verification Cost

Strengthen Verifiable. Verification Cost is a lifecycle **process measure**.
It is **not** evidence that the change is correct.

Definition: the **pre-merge** effort and resource cost required to establish
sufficient confidence in a change.

**Operational cost** is different: **post-merge** runtime / infrastructure cost
caused by the change. It lives under Operational Evidence.

AI-assisted development should evaluate not only whether a change is correct,
but also how expensive it is to verify.

AI-assisted productivity must be evaluated across the full change lifecycle,
not only at the point of code generation.

A change is not necessarily more productive if faster generation creates
disproportionate review, verification, or operational cost.

The following are **optional proxies**, risk-gated, **not** mandatory for every
Low-risk change. Time to merge may include queue time. Static-analysis
*findings* themselves are verification results; the *count or effort* of
resolving them may be a Verification Cost input.

- reviewer iterations
- review comments
- time to merge
- test execution cost
- static-analysis finding count / resolution effort
- human review effort
- unresolved verification uncertainty

### Operational Evidence

**Operational Evidence** is the parent heading. **Performance Evidence** may
include measurable runtime impact. **Operational cost** (post-merge runtime /
infrastructure cost) is recorded here, not as a sibling verification result.

For performance-sensitive changes, consider only metrics relevant to the
change:

- CPU impact
- memory impact
- database queries
- allocations
- latency
- external API calls
- infrastructure cost

Passing functional tests does not prove that generated code is operationally
efficient. N/A is acceptable when performance, cost, or capacity is not in
scope.

### Risk gating

| Evidence | Low | Medium | High / Critical |
| -------- | --- | ------ | --------------- |
| Ambiguity / clarification | One-liner if any; N/A if clear | Only if meaningful questions or assumptions exist | Blocking ambiguity resolved or accepted as residual risk |
| Instruction provenance | Only if this change relied on or modified persistent instructions | Same; not merely because AI was used | Same; do not document files merely because they exist |
| Agent execution evidence | If an agent ran: human, model, accountable owner | Add tools / persistent instructions when relevant | Full set when elevated permissions, MCP, external/production systems, or sensitive data |
| Verification cost | Skip or one line; not every proxy | Brief | Required |
| Operational evidence | Only metrics in scope | If in scope | Required when performance/cost/capacity is in scope |

### Empirical status

Some motivation statements in this RFC are empirical hypotheses or
observations that should be validated through real-world VAD adoption.

Examples of hypotheses or motivating observations (not established facts
without references):

- faster AI generation may shift cost into review and verification
- verification-cost fields are candidate proxies
- MCP/tool execution traces may improve incident investigation

Methodology design claims remain normative and do not depend on any single
productivity study, for example:

- evidence attaches to existing properties
- agent execution evidence is input, not result
- risk level controls evidence depth
- unresolved blocking ambiguity is a stop condition

The evidence model itself does not depend on any single productivity study.

## Alternatives

- New workflow stage 8 (Evidence Pack or Agent Execution): rejected; dilutes
  the seven-stage model. Agent execution evidence is cross-stage, not a stage.
- Sixth required artifact: rejected; duplicates Change Map and Verification Report.
- Seventh core property (for example “Economical”): rejected; verification cost
  strengthens Verifiable rather than adding a property.
- Treating agent logs as a verification result: rejected; they are inputs.
- Treating verification cost as a verification result: rejected; it is a
  process measure.
- Requiring full instruction provenance whenever instruction files exist:
  rejected; record only what this change relied on or modified.

## Risks

- Template bloat and checklist theater (especially mandatory Low-risk metrics).
- Recording prompts, MCP payloads, or logs that contain secrets.
- Treating agent execution records as proof of correctness.
- Placing execution evidence inside the Verification Report so readers treat
  it as a Stage 6 result.
- Triggering Medium-risk ceremony merely because AI assistance was used.

Mitigations: risk gating encoded **in the templates** (N/A captions), no-secrets
rule on templates, explicit “cross-stage input, not result” language, Medium
gates that require meaning (questions, or relied-on/modified persistent
instructions) rather than “AI-assisted.”

## Migration Impact

Additive. Existing 0.1 artifacts remain valid. Teams may ignore new rows on
historical changes. Documented version stays Draft 0.1 until this RFC is
accepted.

## Open Questions

- How much of an agent execution record must be retained, and for how long?
- Should verification cost use hours, story points, or mixed qualitative fields?
- Which operational metrics are minimum for API vs batch vs mobile clients?
- Can CI attach verification-cost and operational-evidence blocks automatically?
- Should instruction provenance eventually use the ADR template for large rule
  changes?
